# 规格：采购任务请求校验、补充恢复与失败可观测性

- 规格编号：`008`
- 状态：已确认（2026-11-02；补充方案数据完整性、交期自然日口径、失败诊断与状态图节点日志规则）
- 实现状态：物料解析恢复、方案数据完整性、交期正确性、失败诊断、对话确认上下文、状态图节点日志与确定性校验分步日志已实现；采购专项及非 Redis/PostgreSQL 回归通过，环境级全量回归待补
- 提出人：采购任务使用者
- 日期：2026-11-02
- 关联需求：修复电装 DENSO U27ETR 采购任务无法继续或启动即失败的问题

## 1. 背景与问题

采购任务在真实使用中出现两类连续性中断：

1. 用户发起采购时未提供收货仓库，任务正确进入“待补充”，但对话侧没有恢复能力，任务面板也只显示提示，导致用户补充信息后仍无法继续。
2. 用户重新发起任务并指定供应商 `DENSO` 后，系统把品牌名当成整数供应商编号，任务创建后立即失败；界面又可能回退显示“解析需求”，无法稳定展示真实错误。
3. 用户提供物料名称并使用 `part_id=null` 的结构化请求时，物料查询已经在数据层找到记录，但解析结果没有回写到请求；方案生成器仍要求 `part_id`，最终把可处理的物料解析问题错误显示为终态 `ANALYSIS_FAILED`。
4. 物料查询已经返回稳定供应商 ID 和历史预计交期，但适配层没有继续补全供应商主体，也没有保留预计交期；方案因此缺少可验证的预计到货日期，并在多次无效重试后显示为通用 `PLAN_VALIDATION_FAILED`。
5. 用户在多轮对话中已经明确型号 `U27ETR` 并确认下单，但主 Agent 调用的结构化请求只提交了品类词“火花塞”，任务因此按泛词查询并返回 `PART_NOT_FOUND`。
6. 用户进一步同时提供 `part_id=65` 与完整名称后，适配器仍先按名称模糊查询并用 ID 过滤；模糊查询为空时，明确有效的 ID 被错误地判定为不存在。

这些问题让用户既无法完成原任务，也无法判断新任务失败的原因。采购流程应当在请求进入执行前完成可判定校验，自动完成确定性解析；只有确实需要用户决策时才进入补充流程。所有可补充问题应一次性展示，并在补充后继续原任务。

## 2. 用户故事

- 作为采购任务发起人，我希望缺少仓库等必填信息时能在任务面板直接补充，以便继续同一个任务而不必重新发起。
- 作为采购任务发起人，我希望指定供应商时系统只使用可唯一识别的供应商，无法识别时明确要求我确认，以便系统不会凭空猜测供应商。
- 作为采购任务发起人，我希望任务失败后看到一致、具体且可处理的错误，以便知道应该补充信息、重试还是重新创建任务。
- 作为采购任务发起人，我希望系统能用物料名称或编码自动找到物料；只有无法唯一识别时才要求我补充，而不是把内部解析错误变成任务失败。
- 作为采购任务发起人，我希望系统完整利用物料记录中的供应商 ID 和价格，并在实际交期缺失时合理使用历史预计交期，以便系统不会把已有依据误判为数据缺失。
- 作为采购任务发起人，我希望确定性校验失败时看到每个具体校验项，而不是只看到笼统的“采购方案未通过校验”。
- 作为采购任务发起人，我希望我在对话中已经明确并由我确认过的物料型号不会在创建任务时丢失，以免系统再次询问或把品类词当作完整物料名称。

## 3. 业务规则

- 任务进入执行前必须完成采购请求结构和基础业务规则校验。
- 预算为空表示不设预算，是合法状态；不得用默认预算替代。
- 仓库、物料、数量等关键信息缺失时必须进入“待补充”，不得猜测或使用默认值。
- 物料名称、物料编码、物料 ID 任一存在即视为具备查询线索；系统应先做确定性物料解析，不得要求用户重复填写已经可查询的 `part_id`。
- 物料名称可能同时包含品牌、型号和品类（如“DENSO U27ETR 火花塞”），且与 ERP 名称词序不同；整句模糊搜索无结果时必须抽取关键词继续查询，并按跨查询命中情况收敛候选。候选仍不唯一时进入补充，不得随机选择。
- 物料可唯一解析时，必须在进入选商前把解析后的 `part_id` 回写到当前请求，同时保留原始名称/编码作为追溯信息。
- 物料无法唯一解析时，任务必须进入“待补充”，列出歧义候选或缺失线索；只有上游服务不可用等非用户可修复情况才允许进入 `awaiting_retry` 或 `failed`。
- 一次校验应聚合所有用户可补充的问题并在同一中断中展示，避免用户逐轮发现新的基础字段缺失。
- 用户指定的供应商只有在能够唯一解析为业务系统中的有效供应商时才可进入分析；无法唯一解析时必须追问，不得把名称直接转成编号，也不得静默改用其他供应商。
- 请求包含明确 `part_id` 时，物料 ID 是权威解析依据，必须直接调用 `part_get`；不得要求名称模糊查询先命中，也不得因名称词序、品牌或品类描述差异否定有效 ID。
- 同时提供 `part_code` 时，可用 `part_get` 返回的正式编码做强一致性校验；编码冲突应进入待补充。名称仅作为业务描述和追溯信息，不覆盖 ID 的权威性。
- 物料记录返回 `supplierId` 时必须使用该稳定 ID 查询供应商主体，并补全正式名称、状态和信用评级；不得把 `supplierId` 当作品牌名，也不得在能读取供应商详情时继续显示合成名称或未知状态。
- 物料记录中的 `purchasePrice` 可作为无历史报价时的采购价来源；供应商主体与采购价必须分别标注来源，不能相互替代。
- 历史订单有实际交期时优先按 `orderTime → actualDeliveryDate` 计算交期；实际交期缺失且存在 `expectedDeliveryDate` 时，可按 `orderTime → expectedDeliveryDate` 估算，并在候选或分析数据中明确标记为预计交期来源。
- 历史交期按 `PROCUREMENT_TIMEZONE` 下的自然日日期差计算，而不是按完整 24 小时周期向下取整；同日为 `0`、次日为 `1`，时间部分不改变业务日差。
- 带时区的历史时间先转换到业务时区再取日期，不能直接剥离时区；无时区的存量时间按 ERP 业务本地时间解释。实际交期和预计交期均早于下单日期时视为无效，不得生成负交期。
- 历史预计交期是确定性数据回退，不是对当前供应商的新承诺；方案仍须以当前日期加上推算交期得到预计到货日，并由既有确定性规则判断是否满足用户要求日期。
- 若实际交期和预计交期都不存在，系统不得编造交期；用户指定要求到货日时必须说明无法验证该日期，且不得对同一不可修复方案进行无意义重复重试。
- 方案预计到货日必须从业务时区下的当前自然日开始计算；任一方案物料缺少交期时不得生成一个看似完整但不完整承诺的整体到货日，校验错误必须指出无法推算交期的物料。
- 当单物料请求只包含品类词（如“火花塞”）且没有 `part_id/part_code` 时，任务工具可从最近一轮用户表达及紧随其后的确认中恢复唯一、明确的产品型号；恢复结果仅追加到 `part_name`，不得生成编号或替换用户原文。
- 型号恢复只接受最近两轮用户消息中的唯一字母数字型号；当前消息不是确认语时不回溯更早历史。没有唯一型号时必须保持原请求并进入待补充，不得跨任务猜测。
- “待补充”任务必须保留原任务及其已有信息；补充成功后继续同一任务。
- 重复提交同一补充内容不得造成重复审批、重复下单或任务版本跳变。
- 已进入终态的任务必须对外保持同一状态和同一失败原因，不得被较早的执行快照覆盖。
- 用户身份与任务归属仍只能由服务端认证和授权决定，前端入口显隐不构成权限边界。
- 采购状态图的每个节点必须在统一边界记录开始和结果日志，日志至少包含 `task_id`、节点名、进入/返回状态、方案版本、审批状态、执行状态、订单号和耗时，能够按 `task_id` 串联一次采购执行。
- 节点抛出人工中断、业务返回失败或发生未处理异常时，必须记录可区分的事件；失败日志必须包含错误码或异常类型，且不得改变节点原有返回值、异常传播或中断语义。
- 条件路由必须记录源节点、路由键和目标节点，使排查者能够确认状态图实际走了哪条分支；成功订单链路必须可还原 `create_order → verify_order → complete_task`。
- 节点日志仅记录诊断白名单摘要，不得记录用户偏好正文、原始采购对话、完整 `CandidateSet`/方案、完整 MCP 响应或异常上下文中的大段上游原文。错误消息需做换行清理和长度上限截断。
- `validate_plan` 必须按确定性检查段分别记录开始、结果、耗时和新增错误/警告。至少覆盖任务、仓库、供应商候选、供应商状态、偏好供应商、条目数、请求物料、候选价格、金额重算、预算、交期和库存检查。
- 校验检查失败时，日志必须包含稳定检查名、错误码、字段路径、是否可重试和截断后的错误消息，使排查者无需复现方案即可判断期望值与实际值的差异；通过或仅有警告时也必须能确认该检查已执行。

| AC-26 | 历史交期按自然日计算 | 下单时间为 9 月 1 日 10:00，实际或预计到货为 9 月 9 日 09:00 | 归一化历史订单 | 交期为 8 个自然日，不因不足完整 24 小时而错误得到 7 天 |
| AC-27 | 跨时区日期不偏移 | 历史时间带 UTC 等时区，且换算后的业务日期与原始日期文本不同 | 归一化历史订单 | 先把时间转换到 `PROCUREMENT_TIMEZONE` 再计算自然日差；无时区存量时间保持其日期语义 |
| AC-28 | 预计到货日基准与缺失诊断正确 | 方案构建时的当前时间带非业务时区，或任一方案物料没有有效交期 | 生成方案并执行确定性校验 | 预计到货日按业务时区当前自然日加最长交期；有物料缺少交期时不编造整体日期，并指出具体物料 |

## 5. 范围

**包含：**

- 采购任务创建前的请求结构与业务字段校验。
- 供应商名称/编号的确定性解析与歧义处理。
- 物料记录中的供应商 ID、采购价及历史预计交期的确定性补全。
- “待补充”任务的补充、提交、恢复和幂等行为。
- 任务卡片、任务面板、任务查询与事件之间的状态及错误一致性。
- 采购状态图节点、中断、异常和条件路由的诊断日志。
- 针对上述场景的后端、前端和端到端测试。
- 受影响的用户说明与接口契约文档更新。

**不包含：**

- 修改供应商选择、评分、采购价优先级或订单执行规则。
- 自动批准、自动绕过审批或自动修改订单。
- 直接修补现有外部任务数据或检查点。
- 处理与本次现象无关的 ERP、认证或记忆模块重构。

## 6. 约束与依赖

- 用户身份必须来自服务端认证，角色和账号状态须在每次请求时回查。
- 任务恢复必须继续校验任务归属；客户端提供的用户身份或角色不得作为授权依据。
- 关键业务字段缺失时必须走人工补充路径，不使用默认值伪造业务数据。
- 恢复不得绕开既有审批、方案哈希、幂等和订单执行保护。
- 现有待补充任务应可通过正式恢复能力继续，不要求迁移或手工修改数据库。

## 7. 非功能要求

- 所有状态、错误和恢复行为必须可测试，不以“体验良好”等主观描述作为验收依据。
- 补充恢复过程中的日志不得记录用户偏好正文；错误记录应保留任务编号、错误码和可诊断上下文。
- 节点日志必须采用统一事件名和字段，不允许各节点任意打印完整状态；错误消息长度上限为 500 个字符。
- 失败恢复和重复提交不得改变除目标任务外的数据。
