# SDD 工作流（本仓库轻量版）

Spec-Driven Development：**先把“要什么”写成可验收的规格，再决定“怎么做”，最后按任务清单实现**。
规格是需求方与实现方之间的契约；代码只是规格的一种实现。

本仓库的 SDD 只保留三个产物，避免小需求被文档淹没：

```text
specs/
  001-<slug>/
    spec.md      # 要什么：背景、场景、验收标准、范围、未决问题（不含技术方案）
    plan.md      # 怎么做：技术选型、改动文件、接口/数据变更、测试策略、风险
    tasks.md     # 按什么顺序做：可勾选任务，每条都有验证方式
  _template/     # 三个模板，复制后改名
```

## 六步流程

### 0. 把需求收敛成一句话（10 分钟）

回答三个问题，写不出来就先别建目录：

- 谁（哪个角色）在什么场景下遇到什么问题？
- 他要完成什么动作、看到什么结果？
- 怎么判断做完了（至少 2 条可测试的验收标准）？

超过 3 个说不清的点，先列成“未决问题”，不要边写代码边猜。

### 1. 写 `spec.md`（只写 What / Why）

复制模板：

```bash
mkdir -p specs/001-your-feature
cp specs/_template/spec.md specs/001-your-feature/spec.md
```

规则：

- **不写**类名、表结构、接口路径、框架选型——这些属于 `plan.md`。
- 每条验收标准必须是 Given/When/Then 或可直接执行的检查，禁止“体验良好”“性能优化”这类不可判定描述。
- 明确写出“不做什么”（Out of Scope），这是控制范围的主要手段。
- 有歧义的地方标 `[待确认]`，集中到“未决问题”，一次问完。

### 2. 规格评审（人工确认，必过）

把 `spec.md` 给需求相关方（或让 Agent 复述一遍）确认：

- 场景是否覆盖真实业务路径？
- 验收标准是否可测试、是否包含异常/边界？
- 范围是否被悄悄扩大？

**评审通过前不写 `plan.md`，更不写代码。** 这是 SDD 与“先写代码再补文档”的分水岭。

### 3. 写 `plan.md`（只写 How）

- 技术方案给 1–2 个选项并说明取舍，不要只列结论。
- 文件清单写到具体路径（如 `src/mcp_server/tools/xxx.py`、`frontend/src/components/Xxx.vue`）。
- 写清接口契约：MCP 工具名与入参/出参、FastAPI 路由、数据库表变更、前端事件。
- 测试策略对应验收标准：哪条标准由哪个测试/评测覆盖。
- 风险与回滚：影响现有流程的地方必须写。

### 4. 写 `tasks.md`（可执行、可验证）

- 任务粒度：一次提交能完成，通常 30–90 分钟。
- 顺序：契约/测试 → 后端 → 前端 → 文档；有依赖的显式标注。
- 每条任务包含：改哪里、对应哪条验收标准、怎么验证。
- 总数控制在 15 条以内；超了说明需求不够小，先拆需求。

### 5. 分批实现

- 按 `tasks.md` 顺序做，做完一条勾一条，不顺带做“以后可能有用”的改动。
- 测试与实现同步写；本仓库统一用 pytest：

  ```bash
  PYTHONPATH=src .venv/bin/python -m pytest tests/test_xxx.py -q
  ```

- 实现中发现规格有问题：**先改 `spec.md` 并重新确认**，再改代码。禁止“代码即规格”。

### 6. 验收与收尾

- 逐条对照 `spec.md` 的验收标准，留下验证证据（测试输出、接口响应、截图）。
- 全量回归：`PYTHONPATH=src .venv/bin/python -m pytest -q`。
- 更新受影响的 README / 技能说明 / API 文档。
- 提交信息带上规格编号，例如：`feat(001): 支持按供应商批量导出比价结果`。

## 小需求的裁剪规则

| 情况 | 做法 |
| --- | --- |
| ≤ 1 人日、单模块 | 只保留 `spec.md` + `tasks.md`，`plan.md` 可并入 tasks 顶部 |
| 纯文案/配置改动 | 一段 spec 描述 + 验收清单即可，不必建目录 |
| 跨前后端或涉及数据变更 | 三个文件都要，且 plan 必须写接口契约与回滚 |
| 探索性需求（还不知道要什么） | 先做 spike，产出结论后再回到第 0 步，spike 代码不进主干 |

## 与 Agent 协作的约定

- 让 Agent 先复述 `spec.md` 再动手；复述偏差就是规格漏洞。
- 每次只喂一个任务，附上 spec 片段与验证命令，避免一次性生成大段代码。
- Agent 提出规格外的改动时，要求它先给出 spec 变更 diff。
- 评审时重点看：验收标准是否被偷换、是否引入未在 plan 中的依赖。

## 可选：使用 Spec Kit 工具链

如果团队希望有 `/specify`、`/plan`、`/tasks` 这类命令和自动化脚本，可引入
[GitHub Spec Kit](https://github.com/github/spec-kit)（`specify init` 会生成 `.specify/` 目录与命令模板）。
对本仓库的小需求，上面的三文件约定已经够用；引入工具链前先确认团队确实需要命令化和模板校验。
